# Vitral Clients Portal

Web app for Vitral, a fashion accessories shop. It manages client records and creates/manages discount vouchers ("vales"). The app does not track purchases — staff decide at the till when a client qualifies for a vale.

## About the owner

Miguel is the only user for now. He works as a systems/support engineer and is building this on the side. Reply in English, in simple, plain language, and explain steps clearly. Ask before big changes.

## Stack

- Next.js 15 (App Router, TypeScript), server actions for data changes
- Supabase: Postgres database and email/password login (row level security on)
- Hosting: Vercel, code on GitHub (`Miguel645/Vitral-Portal-Clientes`)
- Secrets stay in `.env.local` (never commit it). Only the public URL and anon key are used in the app. Never use a service_role key in client-side code.

## Decisions made

- One user for now (the owner). No roles or staff accounts yet.
- Client phone numbers must be ones SMS can reach (`normalizePhone` in `src/lib/phone.ts`: 9 digits starting with 9, or an international number starting with +). Saving a client whose phone already belongs to another client shows a warning once; saving again confirms. Phones are displayed grouped ("912 345 678") via `formatPhone`; client search by phone ignores spaces. After a search the count reads "3 de 120 clientes".
- All forms use `useActionState` (login, client, Criar vales, Campanhas, settings), so an error keeps what was typed; errors appear under the field they are about (`aria-invalid` + `aria-describedby`), in the hint's size but the error colour. Every form has `noValidate`: the browser's English bubbles ("Please fill out this field") never show; the server action checks everything and returns a Portuguese message for the field (e.g. "Escreva o nome do cliente.", "O telemóvel tem de ter 9 dígitos e começar por 9 …", "Escreva o código do vale."). `required` stays on the inputs for screen readers. "Criar vales" submits through `onSubmit` + `startTransition` instead of `action=` because React's automatic form reset would put its radio buttons/tick box back to their first state.
- Client record: name (required), phone (required), email (optional), birth date (optional), promotions consent (tick box).
- Messages: SMS to every client who agreed to promotions; email too, only when the client has an email. Each campaign can also be "SMS only" or "email only".
- Consent matters (EU/Portugal): never message a client without the consent flag, and every message needs an easy way to opt out.
- Planned SMS provider: Twilio. Planned email provider: Resend. Sending must happen on the server, never in the browser.
- Online from day 1.
- Login is on. The login form asks for a username (not an email) and a password; `src/lib/auth.ts` maps the username to an internal email (`<username>@example.com`, domain kept in one constant) and signs in via Supabase `signInWithPassword`. Username must be 3-30 characters: letters, digits, dot, underscore, or hyphen. The login fields have no hints (owner decision). An empty box gets its own message ("Escreva o seu utilizador." / "Escreva a sua palavra-passe."); any other failure (bad format or wrong credentials) shows one generic message, on purpose, so it never reveals which part was wrong (`login` in `src/app/login/actions.ts`, form in `LoginForm.tsx`). There's no sign-up page, and public sign-ups must stay disabled in Supabase (Authentication settings) — the only way to create an account is directly in the Supabase dashboard. All database policies require `authenticated` only (no more anonymous access).
- All site text is in Portuguese (European).
- Vales (see the wording note below for the UI-vs-database naming split): every vale is 8 random uppercase characters, excluding confusing characters (0, O, 1, I). Each vale is either a percentage (`percent`, 1-100) or a fixed euro amount (`amount_eur`, > 0) — never both (database check), shown via `formatDiscount` in `src/lib/discount.ts` ("10%" / "5,00 €"). Optional `note` (staff-only description, e.g. "Saldos de Natal"). Two kinds: `birthday` (automatic) and `manual` (UI label "Manual"). A vale can be checked at `/verificar` (nav label "Verificar vale") or marked as used from `/codes` (nav label "Vales") and from a client's page — marking from a list always goes through the confirmation page `/codes/[id]/use` (`?back=/clients/<id>` returns to the client).
- Birthday vales: one per client per calendar year, for clients with `consent = true`, using the percentage and validity-in-days set on `/settings/birthday`. A client born on 29 Feb counts as 28 Feb in non-leap years. Created automatically once a day by the `/api/cron/birthdays` Vercel Cron job (see `vercel.json`), and can also be run on demand from the settings page. Each newly created birthday vale sends that client one SMS (`BIRTHDAY_SMS_TEMPLATE` in `src/lib/birthdayCodes.ts`, plus the unsubscribe footer), logged in `sms_log` via `sendSms(..., db)` with the admin client; the SMS is sent only right after a successful insert, and the one-birthday-vale-per-year unique index means it can never go out twice. "Today" is always calculated in the Europe/Lisbon timezone.
- No promotions (removed on purpose — the owner found them pointless). Creating vales is independent: `/codes/new` ("Criar vales") picks percentage (pre-filled with 10) or euro amount (starts empty; the preview shows "[desconto]" until a value is typed), validity dates (from/to, default today to today+30), an optional note, who gets them (a search box with a dropdown that filters as you type — picking a client adds them to the list, clears the search and closes the dropdown; or "Todos os clientes"), and how many vales per client (1-10 — the same client can get e.g. two 10% vales). Every vale belongs to a client (no client-less batches). Optionally sends each client one SMS with their code(s) via `sendSms` — only to clients with `consent = true`; the others still get the vale on their record. SMS template placeholders: `{{name}}`, `{{codigo}}` (required; several codes joined with commas), `{{desconto}}`, `{{validade}}`. The default message ("Bom dia {{name}}! Tem um vale de {{desconto}} de desconto na Vitral: {{codigo}}. Use-o até {{validade}}.") switches between singular and plural ("Tem 2 vales…", "Use-os") with the vales-per-client number, unless edited by hand; its only accent is é, which is GSM-7. No hint under the vale SMS text box (owner asked). Every vale SMS gets the same unsubscribe-link footer as campaign SMS (`composeValeMessage` in `src/lib/smsText.ts`), and the preview and the SMS part totals in the "Tem a certeza?" step on `/codes/new` include it — there's no character/part counter line under the message (owner decision, 2026-10-28 — replaces the earlier "no link on vale SMS" decision). Action: `createVales` in `src/app/codes/actions.ts`; form: `src/app/codes/NewValesForm.tsx` (client component, `useActionState`). The page sets `maxDuration = 60` because sending to everyone is sequential. Shortcuts: header button on `/codes`, "Criar vale para este cliente" on `/clients/[id]` (`/codes/new?client=<id>` preselects).
- The old `/balcao` page was removed (owner decision, 2026-10-28); `/balcao` and `/balcao/verificar` redirect to `/verificar` (`next.config.mjs`). Vale creation lives only on the Vales page. `/verificar` ("Verificar vale", its own nav item): type a code (no auto-correct/auto-capitals, max 8 characters, spaces/dashes ignored, the last code is selected for the next check), get a big green "Válido" or red "Não válido" result with a reason and the vale's note, and a "Marcar como usado" button when valid. After marking, it shows a green "Vale marcado como usado." with a "Desfazer" button.
- `/codes/new` asks for a second confirmation ("Tem a certeza?" with vale/SMS/part totals) before creating vales for "Todos os clientes". "Válido até" can't be before "Válido a partir de".
- The birthday cron and the "run now" button use a server-only Supabase client with the `SUPABASE_SERVICE_ROLE_KEY` (bypasses RLS), since they run without a signed-in session. That key must never have a `NEXT_PUBLIC_` prefix and must never be imported into a client component.
- Campaigns (SMS): `src/lib/sms.ts` has one function, `sendSms(to, text)`, server-only. It normalizes the phone number, then either logs the message to `sms_log` as `simulated` (default, nothing is actually sent) or sends it through Twilio when `SMS_MODE=twilio`, logging `sent`/`failed`. Phone numbers: a 9-digit Portuguese number starting with 9 becomes `+351...`; numbers already starting with `+` are kept; anything else is rejected. `{{name}}` in a message template is replaced with the client's first name; every message gets an unsubscribe-link footer appended (`src/lib/smsText.ts`). Every client has a `short_token` (8 random characters a-z/0-9, unique, set by a database trigger) used in all new links as `/u/<short_token>`, and the older `unsubscribe_token` (uuid), kept so links in messages sent before still work (`tokenColumn` in `src/app/u/[token]/tokenColumn.ts` picks the column by the token's shape); the public page `/u/[token]` (allowed without login) shows a "Confirmar cancelamento" button — only pressing it sets `consent = false` (server action, service-role admin client), never just opening the link, because phone apps open links in the background for previews. `/campaigns/new` has the message composer — no hint under the message box and no character/part counter line (owner decision, 2026-10-28) — with `SmsCostWarning` when the text has characters that force the 70-char encoding (a fixed short sentence listing á, ã, õ, ó, í, ú, ê, ç, and saying é, è, à, Ç are fine; it doesn't name the ones found), a preview, and a "send test SMS" button to one phone number only. `/campaigns/log` (opened from a "Ver registo de SMS" button on Definições, which is also the active nav item there; Campanhas itself only links to it in the result after "Enviar a todos") shows the last 50 `sms_log` rows, each as "Beatriz Maia · +351 933 121 526" (just the number when there's no client, e.g. a test or a deleted client). The recipient count ("142 clientes vão receber esta mensagem.") sits in the "Enviar a todos" section. The SMS counter (`countSmsParts`: real GSM-7 set, € and other extension characters count as 2, long messages split into 153/67-character parts) still drives the totals there and in the "Tem a certeza?" step on `/codes/new`. Below the test section, "Enviar a todos" (the page's primary button) opens an in-page summary (recipients — only `consent = true` clients with a phone — SMS parts per message, total parts counted per client's first name, and the preview) with "Cancelar" / "Confirmar envio"; `sendCampaign` in `src/app/campaigns/actions.ts` sends through `sendSms` (so simulation mode applies) in batches of 10, then shows the result with a "Ver registo de SMS" link. `/campaigns/new` sets `maxDuration = 60`.
- Deleting a vale (each row on `/codes`) or a client (header of `/clients/[id]`) is only reachable from a "…" (more actions) menu — `DeleteMenu` in `src/app/_components/DeleteMenu.tsx` (ARIA menu button: arrows/Home/End/Escape/Tab, closes on outside tap). Choosing it opens an in-page confirmation (a native `<dialog>`, never a browser pop-up) that names the item ("Eliminar o vale GFXWFT86?") with "Cancelar" and a red "Eliminar" (`.btn.danger.solid`). The old `/codes/[id]/delete` and `/clients/[id]/delete` pages were removed (owner decision, 2026-10-28). A deleted client's vales stay in the vale list, without a client.
- Wording — consent: the `consent` field is always shown as "Recebe mensagens" / "Não recebe mensagens" in the UI (tags, filters, counts), never "aceitou promoções" or "consentimento". The client-form tick box reads "Este cliente quer receber mensagens da Vitral (promoções, saldos e novidades)". Recipient counts read like "142 clientes vão receber esta mensagem". The unsubscribe page says "Já não vai receber mensagens da Vitral." These are UI-only renames — the database column is still `consent` and nothing about how it's used changed.
- Wording — vales: discount codes/vouchers are always called "vale"/"vales" in the UI (masculine: "o vale", "os vales", "vale ativo", "vale usado"), never "código", **except** the literal 8-character text itself, which is labelled "código do vale" (e.g. "Código do vale: ABCD1234") — that's the one place "código" is still correct. This is a UI-only rename: the database table is still `discount_codes`, the nav/page route is still `/codes`, and `src/app/codes/`, `codes.ts`, `codeStatus` etc. keep their existing names — only on-screen text changed. Vale statuses: "Ativo" / "Por começar" / "Expirado" / "Já usado". Dates are always dd/mm/aaaa (`formatDate` in `src/lib/date.ts`). Date fields never use `<input type="date">` (some browsers show mm/dd/yyyy): they use `DateInput` (`src/app/_components/DateInput.tsx`), a text box with the number keyboard that inserts the slashes while typing and shows a Portuguese error for impossible dates; the server action turns the text into an ISO date with `parseDisplayDate`, so the database still stores ISO dates. Every field has one short hint (a few words saying what to put there, e.g. "Número de 9 dígitos."), but never examples — no "Exemplo: ..." text or "Ex.: ..." placeholders.

## Interface rules (apply to every screen, not just where first introduced)

- Always the light look (white boxes on a light grey page), even when the device is set to dark mode — there is no dark theme (owner decision, 2026-10-28). `globals.css` has only the light colours and `color-scheme: light`.
- Base text size is 19-20px, set via `:root { font-size: 20px }` (19px on phones) so every other size — defined in `rem` in `globals.css` — scales with it and still respects browser zoom. Form labels are at least 1rem and use `var(--ink)` (dark, not `var(--muted)`) for contrast; hints under fields are at least 0.95rem.
- Every button and form control has `min-height: 48px` and generous spacing — easy to tap on a phone, not just a mouse.
- One clear primary button per screen (`.btn.primary`); everything else is a quieter plain `.btn`. A destructive "Eliminar" never sits in a main button row — it lives in the "…" menu (`DeleteMenu`) and always asks for confirmation in-page.
- Status is never colour-only: every `.tag` always contains a word ("Ativo", "Expirado", "Já usado", etc.), colour is just reinforcement.
- Spacing scale: `--sp-4/8/12/16/24/32/48/64` in `globals.css`. All margin/padding/gap values use one of these — never an arbitrary px number. Cards use `--sp-24` padding, form fields (`label`) have `--sp-24` margin-bottom, buttons in an `.actions` row have `--sp-16` gap, list rows are at least 64px tall. `main > * + *` automatically adds `--sp-32` between top-level sections of a page, so pages don't need manual spacing between stacked cards.
- Three page-width containers, applied to `<main>` — pick exactly one per page: `.page-wide` (1100px: lists/dashboards — clients, vales, campaigns log), `.page-medium` (680px: forms — client form, campaigns composer, settings, vale check, vale creation), `.page-narrow` (460px: login, the unsubscribe page, and the mark-used confirmation page). All three use `--sp-24` side padding on desktop, `--sp-16` on phones.
- Consistent page header: `<header className="top">` with the title on the left and the single primary action button on the right (wraps below on phones via flex-wrap); only add a header button when there's one clear primary action for that screen.
- The client edit page (`/clients/[id]`) uses `.client-layout` (a 2-column CSS grid: form left, vales right) inside `.page-wide`; it collapses to one column under 900px. `.big-btn` is the extra-large till button ("Marcar como usado" on `/verificar`). `.preview` is a shaded box for previews/summaries inside a card (never a card inside a card).
- Main navigation is `src/app/_components/TopBar.tsx`, rendered once by the root layout (not per-page) — a "use client" component that reads the URL with `usePathname()` to decide both whether to render at all (hidden on `/login` and `/u/*`) and which nav item is active. Sticky, full width, thin bottom border, inner content capped at the wide container's 1100px/`--sp-24`. Desktop shows all links in a row (`.topbar-link`, active = bold + underline + `aria-current="page"`, never colour alone); under 900px they collapse into a `<details>/<summary>` "Menu" button opening a full-width panel of big links that closes on selection, on a tap outside it, or on Escape. "Sair" sits on the right, small (0.85rem) and in `var(--muted)` (grey, not red), with a ≥44px tap target, separated from the nav links.
- After every save/delete, redirect back with a `message` query param and show it with `<Notice message={message} />` (`src/app/_components/Notice.tsx`: a light tinted box, `role="status"`, and it removes the param from the address bar so a refresh doesn't show it again) at the top of the destination page (e.g. "Cliente guardado.", "Vale eliminado."). Error messages state what to do next, not just that something failed (e.g. "Verifique e tente novamente.").
- Every form button shows progress and is disabled while working ("A guardar…", "A eliminar…"): `SubmitButton` (`src/app/_components/SubmitButton.tsx`, `useFormStatus`) for server-action forms, or the `pending` flag from `useActionState`.
- Tick boxes and radio buttons are 24px (`label.check input`).
- Every field has an `id` and its `<label htmlFor=…>` (also for tick boxes and radio buttons, so they're read out by their text, not "on"); each hint has an id linked with `aria-describedby`, and an error adds its own id to `aria-describedby` plus `aria-invalid`. Radio button pairs sit in a `role="radiogroup"` named by their card heading.
- `src/app/loading.tsx`, `error.tsx` and `not-found.tsx` give Portuguese loading/error/404 screens.
- Keep forms single-column, one screen's worth of related fields at a time; keep rarely-used things (like `/settings/birthday`) off the main flow, reachable from the nav but not front-and-centre.

## Where things are

- `src/app/` pages and server actions
- `src/app/_components/TopBar.tsx` shared sticky top bar, rendered once by `layout.tsx` (Clientes, Vales, Verificar vale, Campanhas, Definições, plus "Sair")
- `src/app/_components/SubmitButton.tsx` submit button with pending text; `Notice.tsx` the success-message box
- `src/app/_components/CopyButton.tsx` small client component, copies a vale code to the clipboard
- `src/app/verificar/` vale check page (`page.tsx`, `CodeInput.tsx`, `actions.ts` with mark-used and undo)
- `src/app/u/[token]/` public unsubscribe page (no login required)
- `src/lib/supabase/server.ts` Supabase client for the server (uses the anon key, respects RLS)
- `src/lib/supabase/admin.ts` server-only Supabase client using the service role key (bypasses RLS) — used by the birthday cron/settings "run now" action and the public unsubscribe page
- `src/lib/birthdayCodes.ts` shared birthday-code logic used by the cron route and the settings page
- `src/lib/codes.ts` random code generator (vales), `generateUniqueCodes` for many at once
- `src/lib/date.ts` date helpers: "today in Europe/Lisbon", dd/mm/aaaa formatting, datetime formatting
- `src/lib/auth.ts` username validation pattern and the username-to-email mapping used for login
- `src/lib/phone.ts` phone number normalization to international format
- `src/lib/smsText.ts` SMS character/part counting (GSM-7 vs UCS-2), `{{name}}` templating, unsubscribe footer — pure, safe to import client-side for the live counter
- `src/lib/sms.ts` the one `sendSms(to, text, clientId?, db?)` function (`db` = the admin client when there's no session, e.g. the birthday cron) — server-only, never import from a client component
- `src/middleware.ts` redirects signed-out visitors to `/login`; `/login` and `/u/*` are the only routes allowed without a session
- `supabase/schema.sql` database setup. Add new tables and policies here, and tell Miguel to run them in the Supabase SQL Editor.
- `supabase/migrations/` one file per database change (also copied into `schema.sql`). Never apply one without telling Miguel first; he runs it in the Supabase SQL Editor.

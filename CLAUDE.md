# Vitral Clients Portal

Web app for Vitral, a fashion accessories shop. It manages client records and creates/manages discount vouchers ("vales"). The app does not track purchases — staff decide at the till when a client qualifies for a vale.

## About the owner

Miguel is the only user for now. He works as a systems/support engineer and is building this on the side. Reply in English, in simple, plain language, and explain steps clearly. Ask before big changes.

## Stack

- Next.js 15 (App Router, TypeScript), server actions for data changes
- Supabase: Postgres database and email/password login (row level security on)
- Hosting: Vercel, code on GitHub (`Miguel645/Vitral-Portal-Clientes`). Functions run in Dublin (`"regions": ["dub1"]` in `vercel.json`), next to the Supabase database in Ireland (owner decision, 2026-10-30) — keep them together, every query crosses between them.
- Secrets stay in `.env.local` (never commit it). Only the public URL and anon key are used in the app. Never use a service_role key in client-side code.

## Decisions made

- One user for now (the owner). No roles or staff accounts yet.
- Client phone numbers must be ones SMS can reach (`normalizePhone` in `src/lib/phone.ts`: 9 digits starting with 9, or an international number starting with +). Saving a client whose phone already belongs to another client shows a warning once; saving again confirms. Phones are displayed grouped ("912 345 678") via `formatPhone`; client search by phone ignores spaces. After a search the count reads "3 de 120 clientes".
- The 1,000-row limit (Supabase returns at most 1,000 rows per request): no page reads a whole table in one request. Lists (clients on `/`, vales on `/codes`) show 100 per page with "Anterior / Seguinte" (`Pager` in `src/app/_components/Pager.tsx`, `?page=`), and their search/status filter runs in the database query (`clientSearchFilter` in `src/lib/clientSearch.ts`: name/email `ilike`, phone digits via a regex that skips spaces, since phones are stored as typed). The client picker on `/codes/new` asks the database as you type (`searchClients` in `src/app/codes/actions.ts`, 20 results); the page itself only loads counts. Sending (campaigns, `createVales` for "Todos os clientes", the campaign editor's totals) and the birthday check read every row with `fetchAll` (`src/lib/fetchAll.ts`, pages of 1,000 ordered by a unique column until a page comes back empty). `generateUniqueCodes` checks candidates 200 at a time. The duplicate-phone check on saving a client only reads clients whose number ends in the same 9 digits. The campaign summary counts its log rows in the database.
- All forms use `useActionState` (login, client, Criar vales, Campanhas, settings), so an error keeps what was typed; errors appear under the field they are about (`aria-invalid` + `aria-describedby`), in the hint's size but the error colour. Every form has `noValidate`: the browser's English bubbles ("Please fill out this field") never show; the server action checks everything and returns a Portuguese message for the field (e.g. "Escreva o nome do cliente.", "O telemóvel tem de ter 9 dígitos e começar por 9 …", "Escreva o código do vale."). `required` stays on the inputs for screen readers. "Criar vales" submits through `onSubmit` + `startTransition` instead of `action=` because React's automatic form reset would put its radio buttons/tick box back to their first state.
- Client record: name (required), phone (required), email (optional), birth date (optional), promotions consent (tick box).
- Messages: SMS to every client who agreed to promotions; email too, only when the client has an email. Each campaign can also be "SMS only" or "email only".
- Consent matters (EU/Portugal): never message a client without the consent flag, and every message needs an easy way to opt out.
- SMS provider: Brevo (owner decision, 2026-10-28 — billed in euros; Twilio stays available as an alternative, and its trial accounts can't send custom text, error 572006). Planned email provider: Resend. Sending must happen on the server, never in the browser.
- Online from day 1.
- Login is on. The login form asks for a username (not an email) and a password; `src/lib/auth.ts` maps the username to an internal email (`<username>@example.com`, domain kept in one constant) and signs in via Supabase `signInWithPassword`. Username must be 3-30 characters: letters, digits, dot, underscore, or hyphen. The login fields have no hints (owner decision). An empty box gets its own message ("Escreva o seu utilizador." / "Escreva a sua palavra-passe."); any other failure (bad format or wrong credentials) shows one generic message, on purpose, so it never reveals which part was wrong (`login` in `src/app/login/actions.ts`, form in `LoginForm.tsx`). There's no sign-up page, and public sign-ups must stay disabled in Supabase (Authentication settings) — the only way to create an account is directly in the Supabase dashboard. All database policies require `authenticated` only (no more anonymous access).
- All site text is in Portuguese (European).
- Vales (see the wording note below for the UI-vs-database naming split): every vale is 8 random uppercase characters, excluding confusing characters (0, O, 1, I). Each vale is either a percentage (`percent`, 1-100) or a fixed euro amount (`amount_eur`, > 0) — never both (database check), shown via `formatDiscount` in `src/lib/discount.ts` ("10%" / "5,00 €"). Optional `note` (staff-only description, e.g. "Saldos de Natal"). Two kinds: `birthday` (automatic) and `manual` (UI label "Manual"). A vale can be checked at `/verificar` (nav label "Verificar vale") or marked as used from `/codes` (nav label "Vales") and from a client's page — marking from a list always goes through the confirmation page `/codes/[id]/use` (`?back=/clients/<id>` returns to the client). Marking as used **deletes** the vale (owner decision, 2026-10-28; the migration also deleted every vale already used): `markValeUsed` in `src/app/codes/markUsed.ts` deletes it only if, in the same database step, it's valid today; "Vale marcado como usado." shows only when a row was actually deleted, otherwise a Portuguese error says what to do next. There is no "Desfazer", no "Usados" filter and no "Já usado" in practice (`used_at` and that status are left over from before). A code that doesn't exist shows "Vale não válido ou expirado." on `/verificar`, and the confirmation page shows the same title when the vale is gone. The confirmation page says when a vale is expired or not started yet instead of offering the button.
- Birthday vales: one per client per calendar year, for clients with `consent = true`, using the percentage and validity-in-days set on `/settings` ("Definições"; the old `/settings/birthday` address redirects there, `next.config.mjs`). A client born on 29 Feb counts as 28 Feb in non-leap years (`isBirthdayOn` in `src/lib/date.ts`). Missed days are caught up (owner decision, 2026-10-29): each run gives the vale for today's birthday or the most recent one in the last 7 days (`birthdayToGive` in `src/lib/birthday.ts`, tested), but only to clients who already existed and received messages on that birthday; a caught-up vale is valid from the birthday itself (so the per-year rule counts the right year, also across New Year) until today + the validity days. Created automatically once a day by the `/api/cron/birthdays` Vercel Cron job at 10:00 Lisbon (owner decision, 2026-10-28; same 09:00 + 10:00 UTC trick as live campaigns, `?utc=9` / `?utc=10`) (see `vercel.json`); there is no "run now" button (the old "Testar agora" card on Definições was removed, owner decision, 2026-10-28). Each newly created birthday vale sends that client one SMS (`BIRTHDAY_SMS_TEMPLATE` in `src/lib/birthdayCodes.ts`, plus the unsubscribe footer), logged in `sms_log` via `sendSms(..., { db })` with the admin client; the SMS is sent only right after a successful insert. Because used vales are deleted, the one-per-year rule lives in `birthday_vales_given` (client_id + year primary key), filled by a database trigger on every birthday vale insert — a second one for the same year fails, so the SMS can never go out twice; the cron checks that table, not `discount_codes`. "Today" is always calculated in the Europe/Lisbon timezone.
- No promotions (removed on purpose — the owner found them pointless). Creating vales is independent: `/codes/new` ("Criar vales") picks percentage (pre-filled with 10) or euro amount (starts empty; the preview shows "[desconto]" until a value is typed), validity dates (from/to, default today to today+30), an optional note, who gets them (a search box with a dropdown that filters as you type — picking a client adds them to the list, clears the search and closes the dropdown; or "Todos os clientes"), and how many vales per client (1-10 — the same client can get e.g. two 10% vales). Every vale belongs to a client (no client-less batches). Optionally sends each client one SMS with their code(s) via `sendSms` — only to clients with `consent = true`; the others still get the vale on their record. SMS template placeholders: `{{name}}`, `{{codigo}}` (required; several codes joined with commas), `{{desconto}}`, `{{validade}}`. The default message ("Bom dia {{name}}! Tem um vale de {{desconto}} de desconto na Vitral: {{codigo}}. Use-o até {{validade}}.") switches between singular and plural ("Tem 2 vales…", "Use-os") with the vales-per-client number, unless edited by hand; its only accent is é, which is GSM-7. No hint under the vale SMS text box (owner asked). Every vale SMS gets the same unsubscribe-link footer as campaign SMS (`composeValeMessage` in `src/lib/smsText.ts`), and the preview and the SMS part totals in the "Tem a certeza?" step on `/codes/new` include it — there's no character/part counter line under the message (owner decision, 2026-10-28 — replaces the earlier "no link on vale SMS" decision). Action: `createVales` in `src/app/codes/actions.ts`; form: `src/app/codes/NewValesForm.tsx` (client component, `useActionState`). With SMS, `createVales` first records the run in `vale_batches` (SMS text, number of recipients, `valid_to`) and gives every vale its `batch_id`, then sends for up to 10 s while the page waits (`runValeBatchStep` in `src/app/codes/valeBatch.ts`); whoever is left gets their SMS from background steps by themselves (see "Background sending"), and the message says "Os outros N SMS estão a ser enviados automaticamente — pode fechar esta página." The Vales page shows "A enviar automaticamente os SMS dos vales: X de Y" (refreshing every 5 s, `AutoRefresh`) until the run is finished. A run's SMS go only to clients who still receive messages, still have a vale from it and have no `sms_log` row with its `batch_id`; once its vales have expired, the rest are not sent. Shortcuts: header button on `/codes`, "Criar vale para este cliente" on `/clients/[id]` (`/codes/new?client=<id>` preselects).
- Welcome SMS ("Mensagem de boas-vindas", 2026-10-28): set on `/settings` in the `welcome_settings` single-row table (`active`, off by default; `sms_text` with `{nome}`/`{vale}`, same "Inserir" buttons, `SmsCostWarning` and "Remover acentos" as campaigns; optional vale `vale_percent` or `vale_amount_eur` + `vale_valid_days`; preview for the sample name "Maria"). Form: `WelcomeForm` (client component, `useActionState` + `startTransition`), action `saveWelcomeSettings`; its save button is a plain `.btn` because the birthday form has the page's primary button. After every client save, `saveClient` calls `welcomeAfterSave` (`src/lib/welcomeSms.ts`): if the client has `consent = true` and `clients.welcome_sent_at` is empty — new client with the tick, or the tick turned on — it claims the client first (sets `welcome_sent_at` only if still empty and consent still on, the same idea as campaigns marked `sent` first, so it never goes out twice), creates the vale if there is one (`manual`, note "Boas-vindas", valid from today for `vale_valid_days` more days), then sends one SMS via `sendSms(..., { kind: "welcome" })` with the unsubscribe footer. If the vale can't be created the claim is given back (saving again retries); once the SMS was attempted the claim stays, even if it failed. While welcome SMS are switched off, consenting clients are only marked (`welcome_sent_at` set, no SMS), so switching it on later never welcomes old clients. The migration marked every client that existed at go-live as welcomed. A missing `APP_URL` stops it before claiming. On failure the client is still saved and the redirect goes to `/clients/<id>` with a Notice ("Cliente guardado, mas a mensagem de boas-vindas não foi enviada: …"). The client form's consent hint shows "Boas-vindas enviada em dd/mm/aaaa" from the latest `sms_log` row with `kind = 'welcome'` and status sent/simulated (`lisbonDate` in `date.ts`). `sms_log.kind` is `'welcome'` for these and empty for everything else; the history's "Vales e aniversários" filter excludes them.
- The old `/balcao` page was removed (owner decision, 2026-10-28); `/balcao` and `/balcao/verificar` redirect to `/verificar` (`next.config.mjs`). Vale creation lives only on the Vales page. `/verificar` ("Verificar vale", its own nav item): type a code (no auto-correct/auto-capitals, max 8 characters, spaces/dashes ignored, the last code is selected for the next check), get a big green "Válido" or red "Não válido" result with a reason and the vale's note, and a "Marcar como usado" button when valid. After marking, it shows a green "Vale marcado como usado." (no undo — the vale is deleted). An unknown code shows "Vale não válido ou expirado."
- `/codes/new` asks for a second confirmation ("Tem a certeza?" with vale/SMS/part totals) before creating vales for "Todos os clientes". "Válido até" can't be before "Válido a partir de".
- The birthday cron uses a server-only Supabase client with the `SUPABASE_SERVICE_ROLE_KEY` (bypasses RLS), since they run without a signed-in session. That key must never have a `NEXT_PUBLIC_` prefix and must never be imported into a client component — `src/lib/supabase/admin.ts` has `import "server-only"`, so the build fails if it ever is.
- Sending layer: `src/lib/messaging/` (server-only). `sendSms(to, text, { clientId?, campaignId?, isTest?, db? })` returns `{ ok, status, providerId, error }` and logs every attempt to `sms_log` (`status`: `simulated` / `sent` / `failed` / `skipped` / `sending`, shown as Simulado / Enviado / Falhou / Ignorado / Interrompido; `error` holds a short Portuguese reason; `provider_id` is the provider's message id). `sendEmail` is a placeholder with the same shape, for when email (Resend) is added. The provider is picked by `MESSAGING_MODE` (`simulation` — the default and anything that isn't `brevo`/`twilio` — or `brevo` or `twilio`); providers live in `src/lib/messaging/providers/`. Brevo (`providers/brevo.ts`, plain `fetch`, no package) posts to `https://api.brevo.com/v3/transactionalSMS/send` (the current endpoint; `/transactionalSMS/sms` is deprecated) with the `api-key` header, `type: "marketing"`, `unicodeEnabled` only when the text isn't GSM-7, and tag `vitral`; it uses `BREVO_API_KEY` and `BREVO_SMS_SENDER` (up to 11 letters/digits, no spaces, e.g. "Vitral"); Brevo error codes (`not_enough_credits`, `account_under_validation`, `unauthorized`, …) become Portuguese messages in `providers/brevoErrors.ts`. That endpoint only confirms Brevo accepted the SMS — delivery problems after that show up in Brevo's own SMS logs, not in `sms_log`. Twilio (`providers/twilio.ts`, plain `fetch` to Twilio's REST API like Brevo — the `twilio` package was removed, 2026-10-28) uses `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` and `TWILIO_SMS_SENDER` (a phone number "+1…" on trial accounts, a name of up to 11 letters/digits like "Vitral" once upgraded, or an "MG…" Messaging Service id). Twilio error codes become Portuguese messages in `providers/twilioErrors.ts` (unverified number on a trial account, invalid number, no balance, …). Invalid phone numbers are not sent and are logged as `skipped` with the reason. While in simulation, `TopBar` shows a banner under the nav: "Modo simulação — nenhuma SMS é enviada de verdade".
- `APP_URL` (the site's address, for the unsubscribe link): when the link is on and `APP_URL` is empty, nothing is sent — `appUrlError()` in `src/lib/optOut.ts` gives the Portuguese error that vale creation with SMS, campaign send/test/continue and the birthday check (settings button and cron, which then returns status 500) stop with, and that the vale/campaign pages show above the form (`previewBaseUrl()` for their previews). `unsubscribeBaseUrl()` throws in that case.
- Random values (vale codes, the test-SMS token) use `crypto.getRandomValues` (`randomString` in `src/lib/codes.ts`), never `Math.random`.
- Phone numbers: a 9-digit Portuguese number starting with 9 becomes `+351...`; numbers already starting with `+` are kept; anything else is rejected. Every SMS (campaign, vale, birthday) ends with the unsubscribe-link footer (`src/lib/smsText.ts`) — the owner chose the link over "responda STOP" (2026-10-28) because a named sender like "Vitral" can't receive replies. `SMS_UNSUBSCRIBE_LINK=off` leaves the footer out of every SMS, previews and SMS counts included (`unsubscribeBaseUrl` in `src/lib/optOut.ts` returns null → `unsubscribeFooter` returns ""); the owner switched it off on 2026-10-28 to save credits while testing — it must be back on before messaging real clients. Every client has a `short_token` (8 random characters a-z/0-9, unique, set by a database trigger) used in all new links as `/u/<short_token>`, and the older `unsubscribe_token` (uuid), kept so links in messages sent before still work (`tokenColumn` in `src/app/u/[token]/tokenColumn.ts` picks the column by the token's shape); the public page `/u/[token]` (allowed without login) shows a "Confirmar cancelamento" button — only pressing it sets `consent = false` (server action, service-role admin client), never just opening the link, because phone apps open links in the background for previews.
- Consent dates: `clients.consent_at` / `email_consent_at` are set by a database trigger when the tick goes on, and cleared when it goes off (clients who consented before 28/10/2026 have no date). The client form shows "Marcado em …" in the consent hint. `email_consent` exists but has no tick box yet — it's for when email sending is added.
- Campaigns (`campaigns` table: name, channel `sms`, `sms_text`, optional vale `vale_percent`/`vale_amount_eur` + `vale_valid_from`/`vale_valid_to`, status `draft`/`sent`, `created_at`, `sent_at`). `/campaigns` lists them ("Rascunho" / "Enviada") with the "Nova campanha" header button and a "Histórico de envios" button. `/campaigns/new` and a draft's `/campaigns/[id]` use `CampaignEditor` (client component, one `useActionState` → `campaignAction` in `src/app/campaigns/actions.ts`, with `intent` = save / test / send, submitted via `startTransition`): name, SMS text with `{nome}` (first name) and `{vale}` (that client's vale code, required when a vale is included) and "Inserir {nome}/{vale}" buttons, `SmsCostWarning` plus a "Remover acentos" button (`removeAccents` in `smsText.ts`), a preview for the first real client who receives messages, "Incluir um vale para cada cliente" (percentage or euro amount + dates — every recipient with a valid number gets their own new `manual` vale with `campaign_id` set and note "Campanha: <name>"), "Enviar teste" (number pre-filled from `TEST_PHONE_NUMBER`, logged with `is_test = true`, `{vale}` becomes `TESTE123`, which can never be a real code), "Guardar rascunho", and "Enviar campanha" (primary) → in-page "Tem a certeza?" with recipients, SMS per message and total, and the vale. No hint under the SMS text box and no character counter (owner decisions). "Enviar campanha" marks the campaign `sent` first (so it can never go out twice; nothing created or sent → back to draft with the error), then sends for up to 10 s while the page waits (`runCampaignStep` in `src/app/campaigns/deliver.ts`: creates the missing vales, reusing ones already made, then sends in groups of 10 with a 500 ms pause) and redirects to the campaign's summary; whoever is left gets it from background steps by themselves (see "Background sending"). There is no "Continuar envio" button (removed, owner decision 2026-10-29). While clients are still missing, the summary shows "A enviar automaticamente: X de Y SMS. Pode fechar esta página." (refreshing every 5 s) and the last sending problem (`campaigns.send_error`); once stopped or past its Fim it shows how many didn't get it. "Enviada em" shows the first SMS's time. `sendSms` writes the `sms_log` row before calling the provider (status `sending`, shown as "Interrompido", with a reason) and updates it with the result, so an SMS cut off by a timeout is never sent again — and if that row can't be written, the SMS isn't sent. Both pages set `maxDuration = 60`.
- Background sending (owner decision, 2026-10-29: big sends must finish by themselves, nobody presses anything): `src/lib/jobs/index.ts`. A send runs in steps of up to 35 s (`STEP_MS`), each in its own function: `startJob({ kind: "campaign" | "vales", id })` POSTs to `/api/cron/send` (with `CRON_SECRET`, on this same site: `VERCEL_PROJECT_PRODUCTION_URL` in production, else `VERCEL_URL`, else `APP_URL`), which answers 202 at once and sends in `after()`. A step takes the row's `sending_until` marker first (`claimLease`, 2 minutes; only one step at a time), sends to whoever is still missing until its time is up, gives the marker back, and if anyone is left starts the next step itself. A step that hits an error saves it in `send_error` and doesn't hand over; it's tried again by the daily 10:00 job, or as soon as someone opens the campaign's summary or the Vales page while no step holds the marker (those pages call `startJob` in `after()`). `sendInGroups` (`src/lib/messaging/groups.ts`, tested) does the groups of 10, the deadline and the stop check. `/campaigns/log` ("Histórico de envios", newest first, last 100) filters by campaign (or "Boas-vindas" / "Vales e aniversários" / "SMS de teste") and status, and shows each row as "Beatriz Maia · +351 933 121 526", then date · campaign, the text, and "Motivo: …" when it failed or was skipped. Definições also links to it. `?client=<id>` shows only that client's messages ("Só as mensagens de …", back link to the client; the filters keep it). Row labels (`STATUS_LABEL`, `statusTagClass`, `sourceLabel`) live in `src/app/campaigns/log/labels.ts`, shared with the client page. History rows are kept 12 months (owner decision, 2026-10-29; the page says so at the bottom): the daily 10:00 campaigns job also calls `archiveOldSmsLog` (`src/lib/messaging/retention.ts`) → the database function `archive_old_sms_log()` (service role only), which in one step adds a campaign's old rows to its totals (`campaigns.archived_sent/_simulated/_failed/_skipped/_interrupted`, `log_archived_at`) and deletes rows older than 12 months — except rows of a campaign still being sent or of an unfinished `vale_batches` run, which stop anyone being texted twice. The campaign summary adds those totals to the log counts, and once `log_archived_at` is set it no longer says how many clients were missed. Old welcome SMS rows go too, so "Boas-vindas enviada em" disappears from the client form after 12 months. The SMS counter (`countSmsParts`: real GSM-7 set, € and other extension characters count as 2, long messages split into 153/67-character parts) drives the totals in the "Tem a certeza?" steps.
- Campaign audience (owner decisions, 2026-10-28 and 2026-10-29): a client only gets a campaign if they already existed and received messages when it went out on its Início. `pendingRecipients` (`src/app/campaigns/recipients.ts`) — used by every send step and the summary, so they always agree — only takes clients with `created_at` before the campaign's `first_sent_at` and who already received messages then (`consentedByFirstSend` in `audience.ts`, uses `consent_at`); "Enviar campanha" passes the cut-off as `cutoff` for its count, before it's saved. The editor's counts are today's clients. There is no sending to "clientes novos".
- Campaign dates (owner decisions, 2026-10-28): every campaign has "Início" (`starts_on`, default today, today or later) and "Fim" (`live_until`; until typed in it follows the vale's "Válido até", else today + 30; not before Início, not after the vale's end) in the editor's "Datas" card. Início today → "Enviar campanha" sends now. Início later → the button reads "Agendar campanha" ("Confirmar agendamento"), the campaign is saved with `status = 'scheduled'` (shown "Agendada" with a notice; it stays editable, and "Guardar rascunho" turns it back into a draft), and the daily job sends it on that day. Sending sets `first_sent_at` (taken before the client list is read; never moves — `sent_at` moves with every run, so the list shows `first_sent_at`). A campaign is "Ativa" (tag, "Até …") while `status = 'sent'`, `stopped_at` is empty and `live_until` is today or later; the summary has a plain "Parar campanha" button (`stopCampaign`). Every day at 10:00 Lisbon, `/api/cron/campaigns` (`runLiveCampaigns` in `src/app/campaigns/live.ts`, admin client) marks scheduled campaigns whose Início has come as `sent` (only if still `scheduled`, setting `first_sent_at`), then starts a background step for every campaign still live (sent, not stopped, Fim today or later) and every unfinished `vale_batches` run — the safety net if a hand-off was ever lost; normally the step finds nobody left. "Parar campanha" (`stopped_at`) is checked before every group of 10, so a step stops right away; deleting the campaign does the same. A scheduled campaign whose Fim passed unsent shows "Não enviada" and asks for new dates. Vercel Cron runs in UTC, so `vercel.json` calls it at 09:00 and 10:00 UTC (`?utc=9` / `?utc=10` keep the two paths apart) and only the run in Lisbon's 10:00 hour does anything (`lisbonHour` in `date.ts`). "Eliminar campanha" (any status) is in the `DeleteMenu` of `/campaigns/[id]` (`deleteCampaign`): the SMS history and the vales it created stay (`campaign_id` set null), and it stops going out.
- Deleting a vale (each row on `/codes`) or a client (header of `/clients/[id]`) is only reachable from a "…" (more actions) menu — `DeleteMenu` in `src/app/_components/DeleteMenu.tsx` (ARIA menu button: arrows/Home/End/Escape/Tab, closes on outside tap). Choosing it opens an in-page confirmation (a native `<dialog>`, never a browser pop-up) that names the item ("Eliminar o vale GFXWFT86?") with "Cancelar" and a red "Eliminar" (`.btn.danger.solid`). The old `/codes/[id]/delete` and `/clients/[id]/delete` pages were removed (owner decision, 2026-10-28). The Expirados tab on `/codes` has a line with the count ("12 vales expirados") and a `DeleteMenu` "Eliminar vales expirados" (owner decision, 2026-10-29; `deleteExpiredCodes` in `src/app/codes/actions.ts`, same rule as the tab: unused and `valid_to` before today), which deletes them all at once after the same in-page confirmation. A deleted client's vales stay in the vale list, without a client.

## Interface rules (apply to every screen, not just where first introduced)

- Always the light look (white boxes on a light grey page), even when the device is set to dark mode — there is no dark theme (owner decision, 2026-10-28). `globals.css` has only the light colours and `color-scheme: light`.
- Base text size is 19-20px, set via `:root { font-size: 20px }` (19px on phones) so every other size — defined in `rem` in `globals.css` — scales with it and still respects browser zoom. Form labels are at least 1rem and use `var(--ink)` (dark, not `var(--muted)`) for contrast; hints under fields are at least 0.95rem.
- Every button and form control has `min-height: 48px` and generous spacing — easy to tap on a phone, not just a mouse. The same goes for every other tap target (2026-10-30, checked on an 11" Android tablet, 800×1280 upright and 1280×800 sideways): top-bar links, the logo and "Sair", back links (`.navlink`), and whole tick-box/radio rows (`label.check`, 48px tall, so the text is part of the target). `:hover` styles sit inside `@media (hover: hover)`, so a tapped row doesn't stay highlighted on a touchscreen. No page may scroll sideways at 800px or 1280px.
- One clear primary button per screen (`.btn.primary`); everything else is a quieter plain `.btn`. A destructive "Eliminar" never sits in a main button row — it lives in the "…" menu (`DeleteMenu`) and always asks for confirmation in-page.
- Filters over a list are tabs (`nav.tabs` with `a.tab`, the active one bold + underlined with `aria-current="page"`), never `.btn.primary` buttons, so the header button stays the screen's only primary one (Vales page, 2026-10-29).
- "Marcar como usado" only appears on vales that are "Ativo" (Vales list and the client page); expired or not-started ones only show their tag.
- Status is never colour-only: every `.tag` always contains a word ("Ativo", "Expirado", "Já usado", etc.), colour is just reinforcement.
- Spacing scale: `--sp-4/8/12/16/24/32/48/64` in `globals.css`. All margin/padding/gap values use one of these — never an arbitrary px number. Cards use `--sp-24` padding, form fields (`label`) have `--sp-24` margin-bottom, buttons in an `.actions` row have `--sp-16` gap, list rows are at least 64px tall; when a row's tag and buttons wrap under its text they sit 16px under it, and inside a card (the client page's columns) they always go under the text, on the left. `main > * + *` automatically adds `--sp-32` between top-level sections of a page, so pages don't need manual spacing between stacked cards.
- Three page-width containers, applied to `<main>` — pick exactly one per page: `.page-wide` (1100px: lists/dashboards — clients, vales, campaigns log), `.page-medium` (680px: forms — client form, campaigns composer, settings, vale check, vale creation), `.page-narrow` (460px: login, the unsubscribe page, and the mark-used confirmation page). All three use `--sp-24` side padding on desktop, `--sp-16` on phones.
- Consistent page header: `<header className="top">` with the title on the left and the single primary action button on the right (wraps below on phones via flex-wrap); only add a header button when there's one clear primary action for that screen.
- The client edit page (`/clients/[id]`) uses `.client-layout` (a 2-column CSS grid: form left; right, the "Vales deste cliente" card and under it "Mensagens enviadas" — the client's last 5 SMS with date · source, text, reason and status tag, and "Ver todas as mensagens" → `/campaigns/log?client=<id>`, 2026-10-29) inside `.page-wide`; it collapses to one column under 900px. `.big-btn` is the extra-large till button ("Marcar como usado" on `/verificar`). `.preview` is a shaded box for previews/summaries inside a card (never a card inside a card).
- Main navigation is `src/app/_components/TopBar.tsx`, rendered once by the root layout (not per-page) — a "use client" component that reads the URL with `usePathname()` to decide both whether to render at all (hidden on `/login` and `/u/*`) and which nav item is active. Sticky, full width, thin bottom border, inner content capped at the wide container's 1100px/`--sp-24`. Desktop shows all links in a row (`.topbar-link`, active = bold + underline + `aria-current="page"`, never colour alone); under 720px (phones; an upright tablet keeps every link in the bar) they collapse into a `<details>/<summary>` "Menu" button opening a full-width panel of big links that closes on selection, on a tap outside it, or on Escape. "Sair" sits on the right, small (0.85rem) and in `var(--muted)` (grey, not red), with a ≥44px tap target, separated from the nav links.
- After every save/delete, redirect back with a `message` query param and show it with `<Notice message={message} />` (`src/app/_components/Notice.tsx`: a light tinted box, `role="status"`, and it removes the param from the address bar so a refresh doesn't show it again) at the top of the destination page (e.g. "Cliente guardado.", "Vale eliminado."). After creating or saving something, go back to its list with `saved=` so it shows there highlighted (`li.just-saved` + a "Acabado de guardar"/"Acabado de criar"/"Acabada de guardar" label, never colour alone): a client goes to `/?saved=<id>` (pinned first, wherever they'd sort), new vales to `/codes?saved=<code,code,…>` (they're newest, so at the top; not passed for more than 100), a saved campaign draft to `/campaigns?saved=<id>` (shown first). `Notice`'s `clear={["saved"]}` removes it from the address bar with the message. On those lists the message (`Notice autoHide`) and the highlight + label (`JustSavedLabel` in `src/app/_components/JustSaved.tsx`, `li.just-saved` fades out in CSS) disappear after 5 seconds (owner decision, 2026-10-28); the row stays where it is. Error notices never auto-hide. Exceptions: sending a campaign goes to its summary page, and a failed welcome SMS goes to the client's page with the reason. Error messages state what to do next, not just that something failed (e.g. "Verifique e tente novamente."). An action that fails redirects with `error=` instead, shown by `<Notice message={errorMessage} param="error" error />` (red, `role="alert"`, never hides by itself). Deleting (vale, client, campaign) and the unsubscribe button check the database result: they only say "eliminado"/cancelled when a row really changed (2026-10-29).
- Every form button shows progress and is disabled while working ("A guardar…", "A eliminar…"): `SubmitButton` (`src/app/_components/SubmitButton.tsx`, `useFormStatus`) for server-action forms, or the `pending` flag from `useActionState`.
- Tick boxes and radio buttons are 24px (`label.check input`).
- Every field has an `id` and its `<label htmlFor=…>` (also for tick boxes and radio buttons, so they're read out by their text, not "on"); each hint has an id linked with `aria-describedby`, and an error adds its own id to `aria-describedby` plus `aria-invalid`. Radio button pairs sit in a `role="radiogroup"` named by their card heading.
- `src/app/loading.tsx`, `error.tsx` and `not-found.tsx` give Portuguese loading/error/404 screens.
- Keep forms single-column, one screen's worth of related fields at a time; keep rarely-used things (like `/settings`) off the main flow, reachable from the nav but not front-and-centre.
